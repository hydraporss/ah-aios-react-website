# WorldForge v0.4 — Sprint 1 Plan, Data Schemas, and Acceptance Checklist

**Milestone:** Claims, Provenance, and Evidence Lineage  
**Sprint 1 scope:** Claim versioning and governed change proposals  
**Status:** Authoritative Sprint 1 implementation contract. The checklist below remains the verification gate; a feature is not considered accepted merely because it is implemented.

## 1. Sprint 1 objective

Make claim revisions reviewable and traceable. A claim in an editable state may be revised directly, creating a new version. An Approved claim is immutable through direct editing: its author submits a change proposal, a reviewer records a decision and rationale, and approval creates a new claim version while preserving the approved version and its state history.

Sprint 1 does not introduce a standalone Evidence registry (Sprint 2), authenticated identities, server persistence, tamper-resistant audit storage, or a general-purpose entity/relationship migration framework.

## 2. Sprint 1 tasks

### S1.1 — Agree on claim lifecycle and invariants

- Define supported claim states and legal transitions, including what state an approved change creates. Recommended default: `Approved` → change proposal → `Approved` new version, with the new version's review record explaining the approval; do not silently reset it to Draft.
- Define which states allow direct editing. Recommended: Draft and Proposed only; Investigated/Validated/Approved/Rejected/Superseded require a change proposal or explicit reopen workflow.
- Define whether a rejected proposal leaves the claim unchanged (yes) and whether multiple open proposals per claim are allowed (recommend one pending proposal per claim for Sprint 1).
- Define stable ID, timestamp, actor-label, rationale-length, and empty-value rules.
- Record these decisions in the implementation and exchange docs before UI work.

**Done when:** state transitions and invariants are written down and each has a matching acceptance criterion.

### S1.2 — Add explicit claim version snapshots

- Keep a stable `claimId` across versions; increment integer `version` for every accepted direct edit or approved proposal.
- Store immutable snapshots in `versions[]` (or keep the existing `previousVersions[]` shape behind a migration adapter). A snapshot contains the full claim content needed to reconstruct that revision, its status, and the event that created it.
- Each snapshot carries `createdByEventId`, linking directly to the audit event that records its creation. Create the event and snapshot as one logical operation and preserve the link during import/export.
- Treat snapshots as immutable value objects: copy nested arrays and objects on creation/import, never retain references to live claim data, and never mutate a stored snapshot. Validate this rule with a test that later edits cannot change earlier nested values.
- Store `previousVersion` on the current claim as a convenience pointer, not as the only history representation.
- Ensure evidence references are version-scoped so later edits cannot rewrite the evidence record for an older claim version. Until Sprint 2, retain legacy embedded evidence links in the snapshot and mark them as legacy references.
- Add a selector/helper that resolves the current version and historical versions without mutating stored objects.
- When a claim advances, mark every still-Proposed change proposal whose `baseVersion` is older than the new current version as `Conflict`; retain its proposed changes and reason for history, and do not treat Conflict as reviewer rejection.

**Done when:** a claim can be reconstructed at any saved version and prior snapshots remain unchanged after later edits.

### S1.3 — Enforce direct-edit rules

- Gate edit controls in the UI by claim state.
- Enforce the same restriction in the state update handler; hiding a button is not enforcement.
- For Draft/Proposed edits, validate entity and source references, capture the old snapshot, increment version, append history, and emit an audit event.
- For other states, reject direct edits with a clear message and preserve all data.
- Avoid mutating React state or nested historical snapshots in place.

**Done when:** the UI and handler both prevent direct edits to protected states and permitted edits create a version and audit event.

### S1.4 — Implement claim change proposal records

- Add browser-local state/persistence for claim change proposals, separate from record-level change requests.
- Proposal form should capture: target claim, requested statement/entity/evidence changes, reason, proposer label, and creation time. Keep the original claim unchanged while Proposed.
- Validate target claim exists, is in a protected state, and requested changes have at least one meaningful difference. Allow multiple proposals against the same base version so concurrency conflicts are represented explicitly rather than hidden by a single-open restriction.
- List proposals on the Claims view or a dedicated subsection with current claim state, requested changes, proposer, timestamp, and status.

**Done when:** submitting a proposal creates a separate object and leaves the claim and its current version untouched.

### S1.5 — Review and resolve proposals

- Capture reviewer label, rationale, outcome, from/to proposal status, and timestamp.
- Allow only legal reviewer transitions such as Proposed → Approved or Rejected; Conflict is a system-detected terminal proposal status for this sprint and cannot be approved/rejected. Prevent duplicate or stale resolutions.
- Rejection records review/audit history and leaves the claim content/version unchanged.
- Approval atomically creates the next claim version, applies proposed changes, records the previous version, adds the review record, resolves the proposal, and emits audit events.
- Before resolution, compare `baseVersion` with the current claim version. On mismatch, mark the proposal Conflict with `conflictDetectedAt` and `conflictReason`; preserve its content and require a fresh proposal. Never silently rebase or overwrite newer claim data.
- After one proposal advances a claim, automatically mark other Proposed proposals based on the older version as Conflict.

**Done when:** approve/reject actions persist complete rationale; approval creates exactly one new version; rejection creates none.

### S1.6 — Add rollback as a new revision

- Provide a compare/select action to restore content from a prior version.
- Rollback must never decrement the version number, erase intervening versions, or rewrite the prior snapshot. It creates a new version whose content matches the selected version and whose event points to `restoredFromVersion`.
- For Approved claims, use the change proposal/review path; do not expose direct rollback.
- Capture actor label, rationale, timestamp, and source version.

**Done when:** rollback restores prior content as a new version and full forward history remains available.

### S1.7 — Audit and workspace exchange

- Add audit events for direct claim edit, proposal created, proposal approved/rejected, and rollback.
- Export claim snapshots, claim proposals, claim reviews, and related audit events in a bumped workspace bundle version.
- Import must validate shape and references before replacing data; support existing v2/v3 bundles by normalizing legacy claims and empty proposal arrays.
- Round-trip test current and historical versions, rejected and pending proposals, review rationale, and legacy bundles.

**Done when:** export→import preserves IDs, version pointers, snapshots, proposals, reviews, and audit linkage; v2/v3 workspaces still import.

### S1.8 — Interaction and accessibility review

- Review empty, loading, validation-error, pending, rejected, approved, conflict, and success states.
- Check keyboard access, visible focus, labels, responsive behavior, and destructive-action clarity.
- Review with representative claim histories and long statements/rationales.

**Done when:** no workflow state is inaccessible or ambiguous at desktop and mobile widths, and prototype boundaries are visible to users.

## 3. Target data schemas

Schemas below are JSON-oriented contracts. IDs are opaque strings. Timestamps are ISO 8601 UTC strings. User labels are claims entered by the local operator and are not authenticated identities. Preserve unrecognized optional fields during import where feasible.

### 3.1 Claim (current projection)

```json
{
  "id": "claim_001",
  "entityId": "nation_aurelis",
  "statement": "Aurelis was founded in 850 AE.",
  "status": "Approved",
  "canonState": "Approved",
  "version": 3,
  "previousVersion": 2,
  "versions": [
    {
      "version": 1,
      "entityId": "nation_aurelis",
      "statement": "Aurelis was founded around 850 AE.",
      "status": "Draft",
      "createdAt": "2026-10-27T09:00:00.000Z",
      "createdBy": "Atlas Researcher",
      "createdByEventId": "evt_0001",
      "changeType": "Created",
      "changeProposalId": null,
      "reviewId": null,
      "restoredFromVersion": null
    },
    {
      "version": 2,
      "entityId": "nation_aurelis",
      "statement": "Aurelis was founded in 850 AE.",
      "status": "Proposed",
      "createdAt": "2026-10-28T09:00:00.000Z",
      "createdBy": "Atlas Researcher",
      "createdByEventId": "evt_0042",
      "changeType": "DirectEdit",
      "changeProposalId": null,
      "reviewId": null,
      "restoredFromVersion": null
    },
    {
      "version": 3,
      "entityId": "nation_aurelis",
      "statement": "Aurelis was founded in 850 AE.",
      "status": "Approved",
      "createdAt": "2026-10-29T09:00:00.000Z",
      "createdBy": "Atlas Researcher",
      "createdByEventId": "evt_0081",
      "changeType": "ApprovedProposal",
      "changeProposalId": "ccp_001",
      "reviewId": "review_019",
      "restoredFromVersion": null
    }
  ],
  "createdAt": "2026-10-27T09:00:00.000Z",
  "updatedAt": "2026-10-29T09:00:00.000Z"
}
```

**Contract notes:** `id` remains stable; `version` equals the current snapshot's version and is monotonically increasing; `previousVersion` equals `version - 1` when version > 1. `versions` is append-only by application behavior. `status`/`canonState` are duplicated only for compatibility during migration and must be kept consistent. Snapshot `sourceIds` and legacy `evidenceLinks` should be included until Sprint 2 moves evidence to first-class objects.

### 3.2 Claim version snapshot

```json
{
  "version": 3,
  "entityId": "nation_aurelis",
  "statement": "Aurelis was founded in 850 AE.",
  "status": "Approved",
  "canonState": "Approved",
  "sourceIds": ["source_004"],
  "evidenceLinks": [
    { "sourceId": "source_004", "assessment": "Supports", "notes": "Founding charter" }
  ],
  "createdAt": "2026-10-29T09:00:00.000Z",
  "createdBy": "Atlas Researcher",
  "createdByEventId": "evt_0081",
  "changeType": "ApprovedProposal",
  "changeProposalId": "ccp_001",
  "reviewId": "review_019",
  "restoredFromVersion": null
}
```

Required change types: `Created`, `DirectEdit`, `StatusChange`, `ApprovedProposal`, `Rollback`. Each `createdByEventId` is required and must resolve to the corresponding audit event for that claim/version (for example, `evt_0001` creates v1, `evt_0042` creates v2, and `evt_0081` creates v3). Do not store mutable references to the current claim inside a snapshot. Claim snapshots MUST NOT contain references to live mutable state. Deep-copy all nested arrays and objects; a snapshot is a self-contained immutable value. `createdByEventId` is the version-to-event link (the `eventId` in the architecture review) and the audit event links back with `claimId` plus `claimVersion`.

### 3.3 Claim Change Proposal

```json
{
  "id": "ccp_001",
  "claimId": "claim_001",
  "baseVersion": 2,
  "status": "Proposed",
  "reason": "The archive establishes an exact founding year.",
  "conflictDetectedAt": null,
  "conflictReason": null,
  "proposedChanges": {
    "statement": "Aurelis was founded in 850 AE.",
    "entityId": "nation_aurelis",
    "sourceIds": ["source_004"]
  },
  "proposedBy": "Atlas Researcher",
  "createdAt": "2026-10-29T08:00:00.000Z",
  "resolvedAt": null,
  "reviewId": null
}
```

`proposedChanges` contains only changed fields; empty proposal objects are invalid. Proposal states: `Proposed`, `Approved`, `Rejected`, `Conflict`; `Withdrawn` is optional and may be deferred. If the claim version advances beyond `baseVersion`, the proposal becomes `Conflict`, with detection time and reason; its proposed content remains preserved and review actions are disabled. Conflict is not a reviewer decision. It must not overwrite claim content and is not automatically rebased.

### 3.4 Review record for a claim proposal

```json
{
  "id": "review_019",
  "targetType": "ClaimChangeProposal",
  "targetId": "ccp_001",
  "claimId": "claim_001",
  "decision": "Approved",
  "fromState": "Proposed",
  "toState": "Approved",
  "reviewer": "Reviewer One",
  "rationale": "The cited charter supports the requested wording.",
  "createdAt": "2026-10-29T09:00:00.000Z"
}
```

### 3.5 Audit event

```json
{
  "id": "evt_0081",
  "at": "2026-10-29T09:00:00.000Z",
  "actor": "Reviewer One (prototype)",
  "action": "Claim change proposal approved",
  "targetType": "ClaimChangeProposal",
  "targetId": "ccp_001",
  "claimId": "claim_001",
  "claimVersion": 3,
  "detail": "Approved proposal ccp_001; version 3 created from version 2."
}
```

Audit events are append-only in normal application flows, but remain editable/deletable in browser storage. They are lineage records, not tamper-proof audit evidence.

### 3.6 Local persistence and exchange envelope

- Local storage should add a dedicated key such as `worldforge.claim-change-proposals.v1`; keep claim reviews in the existing review collection with explicit `targetType`.
- Workspace bundle should increment from v3 to v4 when these objects are introduced.
- v4 bundle additions: `claimChangeProposals`; claims include `versions`; reviews and audit events use the fields above.
- v2/v3 imports normalize current claim fields into a version 1 snapshot when no history exists and initialize `claimChangeProposals: []`.
- Validate unique IDs, claim/entity/source/review/event references, version sequence, legal state values, and proposal base versions. Verify each snapshot `createdByEventId` resolves to an event for the same claim/version. Report invalid rows and avoid silent loss.
- Preserve terminal `Conflict` proposal status and conflict metadata in round trips; a Conflict proposal is historical and requires a new proposal for a newer base version.

## 4. v0.4 acceptance checklist

### A. Claim governance and versioning

- [ ] Claims have a stable ID, entity link, current version, status/canon state, and append-only version snapshots.
- [ ] Every version snapshot contains the claim fields required to reconstruct that historical revision.
- [ ] Every snapshot has a `createdByEventId` that resolves to its creation audit event.
- [ ] Snapshots are deep-copied immutable values; changing current nested fields cannot alter historical snapshots.
- [ ] Draft/Proposed direct edits create a new version and audit event.
- [ ] Validated/Approved/Rejected/Superseded claims cannot be changed through direct edit controls or direct update handlers.
- [ ] An approved claim can be changed only through a separate proposal and review flow.
- [ ] A pending proposal leaves the claim unchanged.
- [ ] Approval creates exactly one next version, links the review and proposal, preserves the previous snapshot, and logs audit events.
- [ ] Rejection preserves claim content/version and records reviewer, rationale, outcome, and time.
- [ ] Stale proposal base versions are detected and cannot overwrite a newer claim.
- [ ] When one proposal advances a claim, other Proposed proposals based on the old version become Conflict and retain their content, reason, and base version.
- [ ] Conflict is distinct from Rejected, records detection time/reason, and cannot be resolved as if it were still Proposed.
- [ ] Rollback creates a new version from a prior snapshot and preserves all intervening history.

### B. First-class evidence registry

- [ ] Evidence has its own stable ID and links one claim to one source.
- [ ] Assessment is one of `Supports`, `Contradicts`, `Contextual`, or `Unassessed`.
- [ ] Evidence notes and creation metadata persist independently from source and claim objects.
- [ ] Evidence registry lists all evidence and filters by claim, source, and assessment.
- [ ] Deleting or importing a linked claim/source handles evidence references explicitly; no silent orphaning.
- [ ] Legacy embedded evidence links migrate or remain readable with documented compatibility behavior.

### C. Provenance timeline

- [ ] Timeline unifies record creation, relationship add/edit, source linking, claim create/edit, evidence add/edit, review, decision, status transition, and approved change events.
- [ ] Events sort chronologically with deterministic ordering for equal timestamps.
- [ ] Filters include object type, object/entity/claim, and date range.
- [ ] Timeline items resolve to the relevant object detail view where the object exists.
- [ ] Missing/deleted object references remain understandable and do not break the view.
- [ ] Empty, invalid date, and no-match filter states are accessible.

### D. Claim-to-decision and review navigation

- [x] Claim view lists linked evidence, reviews, and decisions.

- [x] User can open linked decisions from a claim; decision entries link back to the claim.
- [x] Claim status/canon state is visible alongside these links.
- [x] Missing links are represented clearly and do not crash the UI.

### E. Version comparison

- [x] Claim comparison displays old and new statements and changed metadata/evidence links.
- [x] Relationship comparison shows changed endpoints, type, notes, and evidence references.

### F. Provenance metrics

### G. Exchange, migration, and audit

## 5. Sprint 1 exit gate

- [ ] Every claim change that changes claim content or status creates a new, event-linked version.
- [ ] Approved claims cannot be edited or rolled back directly.
- [ ] Proposal base-version conflicts are detected, retained as `Conflict`, and cannot overwrite newer claims.
- [ ] Rollback restores prior content as a new version while preserving every intervening version.

# Sprint 2 — First-Class Evidence Registry

**Milestone:** First-Class Evidence Registry and Evidence Lineage  
**Status:** Initial implementation is in code and the production build passes. Desktop/mobile interaction, keyboard, and round-trip acceptance checks remain open.

## 1. Sprint 2 objective and scope

Move source assessments out of claim-embedded evidence arrays into independent, versioned Evidence records. Evidence will link one claim to one source and retain assessment, notes, reviews, versions, and audit references. Claims and sources remain separate objects.

Sprint 2 includes evidence CRUD/versioning, evidence review, legacy v4 migration, audit events, and JSON v5 exchange. It does not include a general provenance timeline redesign, version diff viewer, dashboard metrics, evidence scoring, or external source verification.

## 2. Evidence schemas

### 2.1 Evidence record (current projection)

```json
{
  "id": "evidence_001",
  "claimId": "claim_001",
  "sourceId": "source_004",
  "assessment": "Supports",
  "notes": "Founding charter directly states the year.",
  "version": 1,
  "previousVersion": null,
  "versions": [
    {
      "version": 1,
      "assessment": "Supports",
      "notes": "Founding charter directly states the year.",
      "createdAt": "2026-10-29T09:00:00.000Z",
      "createdBy": "Atlas Researcher",
      "eventId": "evt_1001",
      "changeType": "Created"
    }
  ],
  "createdAt": "2026-10-29T09:00:00.000Z",
  "createdBy": "Atlas Researcher",
  "createdByEventId": "evt_1001"
}
```

Allowed assessments are exactly `Supports`, `Contradicts`, `Contextual`, and `Unassessed`. Assessment validation uses this closed set. `id` is stable across revisions; `version` increments monotonically. Version entries are deep-copied immutable values and link to their creation event. Claim/source changes do not silently mutate evidence; broken references must be surfaced and handled through explicit workspace validation or removal flows.

### 2.2 Evidence version snapshot

```json
{
  "version": 2,
  "assessment": "Contextual",
  "notes": "Reclassified after review.",
  "createdAt": "2026-10-30T09:00:00.000Z",
  "createdBy": "Atlas Researcher",
  "createdByEventId": "evt_1002",
  "changeType": "Edited",
  "reviewId": null
}
```

Supported change types: `Created` and `DirectEdit`. Each snapshot stores `eventId` linking it to its audit event. Reviews are separate records and do not mutate evidence snapshots. `previousVersion` points to the preceding integer version and is a convenience field; the version snapshots are the history source.

### 2.3 Evidence review

```json
{
  "id": "evidence_review_001",
  "evidenceId": "evidence_001",
  "evidenceVersion": 1,
  "decision": "Validated",
  "reviewer": "Reviewer One",
  "rationale": "The cited source is a primary historical record.",
  "createdAt": "2026-10-29T10:00:00.000Z",
  "eventId": "evt_1003"
}
```

Reviewer labels are local and unauthenticated. Review decisions and rationale are retained as review records; they do not verify source contents or establish objective truth.

### 2.4 Evidence audit event

```json
{
  "id": "evt_1001",
  "action": "Evidence Created",
  "targetType": "Evidence",
  "targetId": "evidence_001",
  "evidenceId": "evidence_001",
  "claimId": "claim_001",
  "sourceId": "source_004",
  "evidenceVersion": 1,
  "actor": "Atlas Researcher (prototype)",
  "at": "2026-10-29T09:00:00.000Z"
}
```

Every evidence version and review links to its creating event; each event links back to the evidence ID and version. Events cover Created, Edited, Reviewed, Linked, and Unlinked. Local browser history remains editable and is not tamper-proof audit evidence.

## 3. Workspace v5 additions and migration

The v5 bundle keeps the existing workspace collections and adds first-class evidence data:

```json
{
  "format": "AH-AIOS WorldForge workspace bundle",
  "version": 5,
  "claims": [],
  "claimChangeProposals": [],
  "claimReviews": [],
  "evidence": [],
  "evidenceReviews": [],
  "auditEvents": []
}
```

- `claimReviews` carries the existing claim review records; other existing review records remain preserved in their existing review collection or a documented typed equivalent.
- `auditEvents` is the canonical v5 audit collection, carrying the existing v4 audit events plus evidence events. Importers may read the legacy v4 `audit` field and normalize it.
- Export includes records, relationships, sources, decisions, record change requests, claims, claim change proposals, claim reviews, evidence, evidence reviews, and all audit events. No v4 workspace data is dropped.
- v2, v3, and v4 bundles remain importable. For each legacy claim `evidenceLinks[]` item, create one evidence record keyed deterministically by claim ID, source ID, and duplicate occurrence index, preserving assessment, notes, and source reference. Preserve duplicate links as distinct evidence entries; never silently discard data.
- Migration is idempotent: importing and exporting an already migrated workspace must not create duplicate evidence records.
- Validate unique IDs, claim/source references, assessment values, version sequence, review/event references, and event-to-version linkage before replacing current workspace data. Report actionable errors.
